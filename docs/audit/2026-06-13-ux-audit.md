### P2
- Величезний градієнт-хедер 280dp без постера — змарнований простір; великий логотип на афіші.
- Немає «поділитися подією», «додати в календар», вибору кількості квитків (зараз 1 за раз).
- Категорійні чипи — лише з наявних подій, без横 скрол-індикації; немає лічильника.
- Онбординг не пояснює цінність (просто список чипів).
- Коменти без аватарів і відносного часу; чат-полінг 4с без індикатора відправлення.
- Хардкод строк у Kotlin замість strings.xml (ускладнить майбутню локалізацію).

## Технічний аудит UI-шару
- Тема: кольори в `ui/theme/Color.kt` (Accent/Muted) використовуються неконсистентно, частина Color(0xFF...) інлайном (EventCard, деталі).
- Компонентної бібліотеки немає: картки/кнопки/порожні стани зібрані ad-hoc на кожному екрані (3 різні empty-state верстки).
- `EventDetailScreen` бере подію з `afishaVm.find()` — після оновлення списку чи дип-лінку може бути null («Подію не знайдено» при живій події). Потрібен `GET /api/events/:id` (бекенд-прогалина!) — зараз його НЕМає.
- Стан loading/empty/error систематично відсутній (тільки афіша має loader).

## Бекенд-прогалини під повний UX
1. `GET /api/events/:id` — деталі однієї події (для дип-лінків/оновлення).
2. `GET /api/me/unread` — `{notifications, messages}` для бейджів.
3. Фільтр минулих в `list_events` (+ `past=true` параметр), заборона купівлі/резерву минулих, заборона відгуку до початку.
4. Для веб-кабінету організатора: агрегати продажів, список квитків події, payout requests (Фаза 3).
5. Для адмінки: admin-списки users/events/orders з пагінацією, escrow-дії, complaints (Фаза 4).

## Дуальність юзер⇄мейкер (рішення)
Без окремої ролі: **прогресивне розкриття**. Всі бачать «Мої» з вкладками Квитки|Мої події;
створення доступне всім; інструменти мейкера (QR-скан, керування) з'являються лише коли є ≥1 власна
подія. Окремий перемикач у профілі не потрібен — менше станів, нуль бар'єрів для першої події.
