# REF-7 — Повернення з ініціативи організатора: один квиток, з причиною, видимою покупцеві

| Поле | Значення |
|---|---|
| **Фаза** | Фаза 2 — повернення |
| **Estimation** | M |
| **Status** | `INTAKE` |
| **Критичний шлях до першого платежу** | ні |
| **Depends on** | REF-5, REF-6 |

## Навіщо

Вимога власника — щоб можна було повернути гроші, а не тільки щоб покупець сам це робив. Сьогодні єдиний шлях повернути квиток проти волі покупця — `admin.rs::escrow_action` під платформним адміном; організатор такої можливості не має взагалі. На практиці саме організатор першим дізнається, що людина не прийде, що продали дубль, що гість переплатив або що когось треба зняти з події за поведінку. Без цього кожен такий випадок їде в підтримку платформи.

## Як це працює

Організатор у списку проданих квитків події (наявний GET /api/organizer/events/:id/tickets) біля кожного квитка має дію «Повернути кошти». Тап відкриває форму:

«Повернути кошти покупцеві {ім'я}?
Сума до повернення: [1000 ₴] (можна зменшити)
Причина — покупець її побачить:
( ) Подія змінилась
( ) Технічна помилка з квитком
( ) На прохання покупця
( ) Своя причина: [____]
[Скасувати]  [Повернути кошти]»

Організатор може повернути БУДЬ-КОЛИ, поки кошти не виплачені (escrow ∈ held|clearing|cleared), навіть якщо дедлайн політики для покупця вже минув — політика обмежує покупця, а не організатора. Після 'paid_out' — 409 «Кошти за цю подію вже виплачені. Повернення тепер лише через підтримку.»

Покупець бачить у квитку: «Організатор повернув ваш квиток 12 бер. Причина: подія змінилась. Повернено 1000 ₴ — гроші йдуть на картку 5–10 робочих днів.» І отримує сповіщення (наявна черга notifications + email outbox) із тим самим текстом.

Місце звільняється, промокод повертається, ескроу зменшується — рівно ті самі наслідки, що при самоповерненні (одна функція, три ініціатори).

Поле «Причина» обов'язкове: без неї покупець отримає повернення без пояснення й піде в підтримку або в банк — а в моделі direct charges чарджбек б'є по цьому ж організатору.

ПОМІЧНИКИ. У Фазі 2 повертати кошти може ЛИШЕ організатор події. Наявний event_staff має єдиний дозвіл 'scan' — дозвіл 'refund' для менеджерів вводиться в Фазі 3 (ролі), і цей ендпоінт має бути написаний так, щоб перевірка дозволу була одним викликом, а не розсипана по коду.

## Зміни в API

Новий ендпоінт у наявному `api/src/organizer.rs` (не в admin.rs — це не платформний адмін):
- `POST /api/organizer/tickets/:ticketId/refund` з тілом `{ amount: Option<Decimal>, reason_code: String, reason_text: Option<String> }` → `{ ticket, refunded_amount, currency }`.
- Авторизація: власник події квитка (наявний патерн require_owner з events.rs, застосований через event_id квитка). Точка розширення для staff-дозволу — одна функція `can_refund(db, user, event_id)`.
- Тіло виконання — ТА САМА транзакційна функція, що й у REF-5 (`tickets::do_refund(conn, ticket_id, amount, initiator)`), щоб три ініціатори не розійшлися в наслідках. `return_ticket` після цієї задачі стає тонкою обгорткою над нею з перевіркою політики.
- Причина пишеться в новий рядок `refund_records` і в наявний audit-журнал.

## Зміни в базі

Міграція `0043_refund_records.sql`:
CREATE TABLE refund_records (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  order_id UUID NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  ticket_id UUID REFERENCES tickets(id) ON DELETE SET NULL,
  amount NUMERIC(12,2) NOT NULL CHECK (amount > 0),
  initiator TEXT NOT NULL CHECK (initiator IN ('buyer','organizer','cancellation','admin')),
  initiated_by UUID REFERENCES users(id) ON DELETE SET NULL,
  reason_code TEXT NOT NULL,
  reason_text TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX refund_records_order_idx ON refund_records (order_id);
Це єдине джерело правди для «чому повернули» — і для покупця, і для звіту організатора (REF-9), і для спору з банком.

## Поверхні

**Веб.** `web/app/organizer/[eventId]/page.tsx`: у списку квитків дія «Повернути кошти» + модалка з причиною; у `web/app/me/tickets/page.tsx` — рядок із причиною для покупця.

**Android.** `ui/events/MyEventsScreen.kt` / екран події організатора: та сама дія в списку квитків із BottomSheet вибору причини; у квитку покупця — рядок із причиною.

**Telegram Mini App.** Немає — Фаза 5; ендпоінт готовий і TMA підключить його без змін бекенду.

## Критерії приймання (AC)

- Організатор повертає квиток своєї події зі станом escrow='cleared' → 200, refunded_amount = запитана сума, у refund_records рядок з initiator='organizer' і причиною.
- Той самий виклик при escrow='paid_out' → 409 «Кошти за цю подію вже виплачені…».
- Повернення після того, як дедлайн політики для покупця минув, організатором → 200 (політика обмежує покупця, не організатора).
- Запит без reason_code → 400 «Вкажіть причину — покупець її побачить».
- Покупець у GET /api/tickets/:id бачить причину дослівно тим текстом, що обрав організатор.
- Створюється сповіщення покупцеві (рядок у notifications) і рядок в email outbox із тим самим текстом.
- Місце повертається в продаж (з тією ж стелею tickets_total) і промо-використання відновлюється — рівно як у REF-5, бо код спільний.
- Часткова сума від організатора (400 із 1000) дає refunded_amount=400 і status='partly_refunded'.
- Дія записана в наявний audit-журнал з actor = організатор.

## Що має бути відхилено (SEC)

- Організатор ІНШОЇ події викликає refund для чужого квитка → 403; жодних даних квитка у відповіді.
- Помічник із event_staff.permission='scan' викликає refund → 403 (у Фазі 2 дозволу 'refund' не існує; тест має червоніти, якщо хтось помилково дозволить усім staff).
- Неавторизований виклик → 401.
- amount більше за залишок (amount - refunded_amount) → 409; amount <= 0 → 400.
- Повторний виклик із тим самим ticket_id для вже повністю поверненого квитка → 409, другий рядок у refund_records не створюється.
- reason_text не рендериться як HTML на жодній поверхні (покупець бачить текст, введений іншою людиною — це вектор XSS у веб-клієнті й у листі).
- reason_text обмежений довжиною (напр. 500 символів) → 400 при перевищенні, щоб не роздувати лист і сповіщення.
- Організатор не може повернути кошти на свій рахунок: адресат рефанду завжди платник замовлення, з жодного шляху не переозначується.
