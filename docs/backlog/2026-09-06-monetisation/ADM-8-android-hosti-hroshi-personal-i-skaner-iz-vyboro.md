# ADM-8 — Android: гості, гроші, персонал і сканер із вибором події — друга половина адмінки

| Поле | Значення |
|---|---|
| **Фаза** | Фаза 4 — адмінка на трьох поверхнях |
| **Estimation** | M |
| **Status** | `INTAKE` |
| **Критичний шлях до першого платежу** | ні |
| **Depends on** | ROLE-2, ROLE-3, SCAN-4, ADM-7 |

## Навіщо

ADM-7 закриває саму подію; ця задача — усе, що навколо неї у вечір продажу й у вечір самої події. Без списку гостей з пошуком організатор на дверях безпорадний («я купив, у мене не відкривається пошта»), а без екрана грошей він не знає, коли отримає виплату. Наявний `GET /api/events/:id/tickets` і `GET /api/organizer/payouts` дають дані — бракує екранів.

## Як це працює

ГОСТІ — список квитків з миттєвим пошуком за іменем або останніми 4 символами id квитка (саме так шукають на дверях, коли людина показує лист), фільтри «усі / увійшли / не увійшли / повернені», лічильник угорі. Тап на гостя — картка: ім'я, тариф, ціна, статус, час входу і хто провів, дії «Провести вручну» (Cap::Scan, з обов'язковою причиною — рятує, коли телефон гостя розрядився) і «Запросити повернення» (ROLE-3, лише менеджер і власник).

ГРОШІ — п'ять цифр великим шрифтом: виручка, в ескроу, до виплати, виплачено, і головне — ДАТА найближчої виплати з поясненням, чому саме вона така («після події + 3 дні, але не раніше кінця вікна повернень»). Нижче історія виплат (`GET /api/organizer/payouts` уже є). Менеджер бачить перші чотири цифри без банківських реквізитів і без історії виплат.

ПЕРСОНАЛ — з ROLE-2: список ролей, свайп-відкликання, FAB «Запросити» → системний share-лист із `underground://staff/<token>`.

СКАНЕР — спочатку список подій з `GET /api/me/staff/events` (уже є), де кожна подія показує роль і «увійшло N з M», далі повноекранний сканер із SCAN-4 і кнопкою «Підготувати офлайн» із SCAN-5.

## Зміни в API

`GET /api/events/:id/tickets` (наявний `organizer::event_tickets`) розширюється параметрами `?q=&status=&limit=&cursor=` і полями відповіді `checked_in_at`, `checked_in_by_name`, `tier_name`, `order_id` (order_id — лише для Cap::ViewGuests). Нове: `POST /api/events/:id/checkins/manual {ticket_id, reason}` (Cap::Scan) — ручний вхід без QR, пишеться в `checkins` з `source='online'` і причиною. `GET /api/organizer/payouts` розширюється полем `next_payout_due_at` і `next_payout_reason`.

## Зміни в базі

`ALTER TABLE checkins ADD COLUMN manual_reason TEXT`. Індекс під пошук: `CREATE INDEX tickets_event_owner_idx ON tickets (event_id) INCLUDE (owner_id, status)` та тригерний/функціональний індекс під пошук по імені власника (`users.name`) — конкретна форма визначається планом запиту на сіді.

## Поверхні

**Веб.** Немає (паритет — ADM-9), але ендпоінти спільні.

**Android.** Нові екрани: `GuestsScreen` (пошук, фільтри, віртуалізований список), `GuestSheet` (картка гостя з діями), `MoneyScreen`, `StaffScreen`, `ScanEventPickerScreen`. Пошук працює локально по вже завантаженій сторінці ПЛЮС серверний `?q=` для довгих списків — на дверях затримка в 300 мс помітна.

**Telegram Mini App.** Немає (TMA-14).

## Критерії приймання (AC)

- Пошук «Мар» знаходить «Марія Ковальчук»; пошук за 4 символами id знаходить рівно один квиток.
- Фільтр «не увійшли» показує рівно `sold - checked_in` рядків.
- «Провести вручну» без причини → кнопка неактивна; з причиною → рядок у `checkins` з `manual_reason` і квиток стає `used`.
- Ручний вхід уже проведеного квитка → жовтий вердикт «уже входив», другий рядок `valid` у `checkins` не з'являється.
- Екран «Гроші» показує `next_payout_due_at` і людський текст причини; для менеджера екран не містить IBAN/реквізитів і історії виплат.
- Список подій сканера показує роль і лічильник входів для кожної події з `GET /api/me/staff/events`.
- Список гостей на 3000 квитків гортається без ривків (пагінація по 100, віртуалізація).

## Що має бути відхилено (SEC)

- Контролер відкриває `GET /api/events/:id/tickets` → 403 — список гостей не є частиною роботи на дверях.
- Менеджер отримує список гостей БЕЗ email і телефону; тест перевіряє точний набір ключів у відповіді для ролі Manager.
- `POST /api/events/:id/checkins/manual` контролером дозволено (це його робота), але `reason` обов'язковий і потрапляє в `audit`; ручний вхід чужої події → 403.
- Ручний вхід повернутого або скасованого квитка → 409, стан не змінено.
- `?q=` не дозволяє SQL-ін'єкцію (параметризований запит) і обмежений 64 символами; порожній `q` не витягує всю таблицю без `limit`.
- `cursor` пагінації підписаний або є непередбачуваним id — підміна курсора не дає вийти за межі події.
- «Запросити повернення» на екрані гостя не показується контролеру і відхиляється сервером (ROLE-3).
- Share-лист з інвайт-посиланням не пише токен у системний лог (`Log.d`) — grep по клієнту не знаходить логування токена.
