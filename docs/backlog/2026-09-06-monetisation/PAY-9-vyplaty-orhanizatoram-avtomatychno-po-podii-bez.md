## Навіщо

Сьогодні виплата — ручна дія адміна по організатору, і в ній три реальні дефекти. (1) CTE `to_pay` — звичайний SELECT без `FOR UPDATE`, `marked` оновлює без повторної перевірки `escrow_status='cleared'`, транзакція в READ COMMITTED: два паралельні виклики (два адміни, дабл-клік) обидва створять рядок виплати. Сьогодні це брехня в леджері, після підключення провайдера — дві реальні виплати. (2) `payouts.status` має DEFAULT 'paid' — рядок бреше з моменту вставки, а `orders.escrow_status='paid_out'` ставиться в тій самій транзакції, тож при падінні виплати повторити її неможливо без ручного SQL по проду (що заборонено §9). (3) `create_payout` взагалі не звертається до провайдера — лише пише рядок у леджер. Вимога власника «подія пройшла → виплатили організатору» без цієї задачі не виконується.

## Як це працює

Організатор нічого не робить. Після події гроші дозрівають (PAY-8), і в призначену дату система сама створює виплату на його банківський рахунок у провайдера. У кабінеті організатора є розділ «Виплати»: рядок на кожну виплату — сума, валюта, за яку подію, статус («у дорозі», «виплачено {дата}», «не пройшла: {причина}»), і скільки ще дозріває («очікує виплати {дата}: 12 400 ₴»). Якщо виплата не пройшла (порожній баланс, резерв провайдера, проблема з банком), організатор бачить причину людською мовою і кнопку «повторити», а система і сама повторить через добу. Адмін бачить те саме по всіх організаторах і має ручний оверрайд.

## Зміни в API

Розширює `payouts.rs`. Новий фоновий воркер `payouts::settle_worker` у `main.rs`: бере `cleared`-замовлення пачкою через `SELECT ... FOR UPDATE SKIP LOCKED`, групує по (організатор, подія, валюта), створює рядок `payouts` зі `status='pending'` і детермінованим `idempotency_key`, комітить, і лише ПОТІМ кличе `provider.transfer_payout`. Одна репліка за раз — `pg_advisory_xact_lock` на ключі воркера (sweep у `main.rs` крутиться в кожній репліці). `payouts::apply_provider_status(provider_ref, status, reason)` викликається з вебхука: `paid` → рядок `paid`; `failed` → рядок `failed` + повернення відповідних замовлень з `paid_out` у `cleared` (тобто виплата стає повторюваною без SQL). Наявний `POST /api/admin/organizers/:id/payout` лишається як ручний оверрайд, але переводиться на ту саму безпечну реалізацію. Новий `GET /api/me/payouts` — виплати організатора + сума, що дозріває.

## Зміни в базі

Міграція 0047: `ALTER TABLE payouts ALTER COLUMN status SET DEFAULT 'pending'`; бекфіл наявних рядків не потрібен (історія лишається як є, зафіксувати в коментарі міграції); `ADD COLUMN idempotency_key TEXT`, `CREATE UNIQUE INDEX payouts_idem_uidx ON payouts (idempotency_key) WHERE idempotency_key IS NOT NULL`; `ADD COLUMN event_id UUID REFERENCES events(id)`, `ADD COLUMN amount_minor BIGINT`; нова таблиця зв'язку `payout_orders (payout_id UUID REFERENCES payouts(id) ON DELETE CASCADE, order_id UUID REFERENCES orders(id), PRIMARY KEY (payout_id, order_id))` — сьогодні зв'язку виплати з конкретними замовленнями немає взагалі, тож при `failed` неможливо дізнатись, які замовлення повертати в `cleared`.

## Поверхні

**Веб.** Кабінет організатора → «Виплати»: список із сумою, подією, статусом, причиною відмови, кнопкою «повторити»; зверху «дозріває до виплати: {сума} — {дата}». Адмінка → «Виплати»: те саме по всіх, плюс ручний оверрайд статусу (наявний `PATCH`).

## Критерії приймання (AC)

- Два паралельні виклики створення виплати для одного організатора створюють РІВНО ОДИН рядок у `payouts` (тест із двома одночасними транзакціями).
- Дабл-клік по ручній виплаті не створює другого рядка: унікальний індекс `idempotency_key` тримає.
- Новий рядок виплати створюється зі `status='pending'`, а не `'paid'` (control-presence: повернути DEFAULT 'paid' — тест червоніє).
- `PayoutFailed` з вебхука повертає всі замовлення цієї виплати з `paid_out` у `cleared`, і наступний прохід воркера створює НОВУ виплату — без жодного ручного SQL.
- Виплата не створюється для організатора з `psp_payouts_enabled = false` — замовлення лишаються `cleared`, у кабінеті видно причину.
- Воркер, запущений у двох репліках одночасно, створює один комплект виплат (перевіряється advisory-локом у тесті).
- `GET /api/me/payouts` показує лише власні виплати; чужий організатор у відповіді не з'являється.

## Що має бути відхилено (SEC)

- Організатор не може ініціювати виплату собі раніше строку: ендпоінт «повторити» діє лише на виплату у стані `failed`, і лише на власну.
- Комісія платформи не знімається вдруге при сетлменті (див. PAY-10) — тест на суму виплати проти суми `application_fee` замовлень.
- Виплата на суму, більшу за суму пов'язаних замовлень мінус комісія, неможлива — CHECK і тест.
- Заблокований або GDPR-видалений організатор не отримує виплат: наявний гейт `blocked` зберігається, control-presence тест.
- Ручний адмінський оверрайд статусу пишеться в `admin_actions` з попереднім і новим значенням.
- Виплата в нульовій або від'ємній сумі не створюється і не надсилається провайдеру.
