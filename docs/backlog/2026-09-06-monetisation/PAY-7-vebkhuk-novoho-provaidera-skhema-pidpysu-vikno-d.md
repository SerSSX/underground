## Навіщо

Наявні `sign`/`verify_signature` у `webhooks.rs` — це простий hex-HMAC над тілом під заголовком `x-signature`. Обраний провайдер надсилає складений заголовок виду `t=<мітка часу>,v1=<підпис>`, підписує конкатенацію `мітка + "." + тіло`, під час ротації секрету надсилає КІЛЬКА підписів v1, і вимагає перевірки давності мітки. Тобто переїжджає лише constant-time порівняння і SERIALIZABLE-ідемпотентність — решта пишеться наново. Плюс події під'єднаних акаунтів несуть поле акаунта, і без його обробки ми не дізнаємось ні про завершення онбордингу, ні про виплату, ні про диспут.

## Як це працює

Для людини невидимо, але це нерв усієї системи. Провайдер підтверджує оплату → протягом секунд покупець бачить квиток. Провайдер повідомляє про повернення → квиток стає «повернений», покупець бачить це в своїх квитках. Провайдер повідомляє про спір (чарджбек) → замовлення заморожується, організатор бачить у кабінеті «спір по замовленню», виплата по цій події призупиняється. Провайдер повідомляє, що виплата пройшла або впала → організатор бачить відповідний статус у розділі виплат із причиною. Якщо провайдер надсилає подію, якої ми не розуміємо, ми відповідаємо «прийнято» і нічого не робимо — щоб він не ретраїв нескінченно.

## Зміни в API

`POST /api/webhooks/psp` замінює `POST /api/webhooks/lemonsqueezy` (старий маршрут лишається до PAY-12). `psp::Psp::verify_webhook` реалізує: розбір складеного заголовка, ігнорування всіх схем, крім `v1` (захист від downgrade), перевірку КОЖНОГО з наданих `v1` у constant time, відхилення мітки старшої за 5 хвилин, і мапінг у `WebhookEvent`. Маршрутизація в `webhooks.rs`: `Paid` → `orders::fulfill`; `Refunded` → `orders::mark_refunded`; `Disputed` → `orders::freeze` + сповіщення організатора; `PayoutPaid`/`PayoutFailed` → `payouts::apply_provider_status`; `AccountUpdated` → `kyc::apply_account_status`. Кожна оброблена подія спершу пишеться в `webhook_events` (PK `(provider, event_id)`), і конфлікт = тихий 200.

## Зміни в базі

Немає нових таблиць — використовує `webhook_events`, `orders.terminal_event_seen` і `orders.provider_ref` з PAY-1. Додається `ALTER TABLE payouts ADD COLUMN provider_ref TEXT UNIQUE` (щоб `PayoutPaid`/`PayoutFailed` знаходили свій рядок).

## Критерії приймання (AC)

- Вебхук із правильним підписом і свіжою міткою обробляється (200); той самий із міткою 10-хвилинної давності — 401.
- Заголовок із кількома `v1` (ротація секрету) приймається, якщо ХОЧА Б один збігається зі старим або новим секретом.
- Заголовок зі схемою `v0` і без жодного `v1` — 401, а не «прийнято».
- Підміна одного байта в тілі при незмінному підписі — 401.
- Подія типу, якого ми не обробляємо, повертає 200 і не створює жодного побічного ефекту, окрім рядка в `webhook_events`.
- `PayoutFailed` з причиною `insufficient_funds` повертає відповідні замовлення зі стану `paid_out` у `cleared`, а виплату позначає `failed` із причиною (див. PAY-9).
- Повторна доставка `Disputed` не заморожує двічі і не шле другого сповіщення.

## Що має бути відхилено (SEC)

- Порівняння підписів ТІЛЬКИ в constant time — control-presence тест: заміна на `==` має завалити окремий тест, що перевіряє використання `verify_slice`.
- Тіло вебхука не парситься до перевірки підпису (порядок операцій перевіряється тестом на невалідний JSON із правильним підписом → 400, і на валідний JSON з неправильним підписом → 401 БЕЗ спроби розбору).
- Тіло більше за ліміт (напр. 1 МБ) відхиляється до обчислення HMAC.
- Подія з полем акаунта, що не належить жодному нашому організатору, не застосовується — 200 без дії.
- `Paid` для замовлення з `terminal_event_seen IS NOT NULL` не мінтить квиток (захист від позачергової доставки).
- Секрет вебхука для test і live не взаємозамінні: подія, підписана тестовим секретом у live-режимі, — 401.
