# REF-8 — Скасування події → автоматичне 100% повернення всім, через чергу з ретраями

| Поле | Значення |
|---|---|
| **Фаза** | Фаза 2 — повернення |
| **Estimation** | L |
| **Status** | `INTAKE` |
| **Критичний шлях до першого платежу** | ні |
| **Depends on** | REF-6, REF-7 |

## Навіщо

Це найгірша діра фази і водночас юридичний мінімум: `events.rs::delete_event` виконує рівно `UPDATE events SET status='cancelled', sales_closed=true` — і НЕ торкається orders, tickets чи ескроу. Кошти скасованої події сьогодні спокійно дозрівають через sweep і виплачуються організатору. Масового повернення немає ніде: `admin.rs::escrow_action` працює по ОДНОМУ замовленню за HTTP-виклик, тож 200 квитків — це 200 ручних викликів без ретраїв. При цьому «скасували — повернули 100%» це не фіча, а вимога закону (в Україні при скасуванні/перенесенні повернення обов'язкове; в ЄС «no refund» законний лише для датованої події, що відбулась). Жодна політика організатора цю гілку вимкнути не може.

## Як це працює

Організатор натискає «Скасувати подію». Перед підтвердженням бачить дослівно:

«Скасувати «{назва}»?
Продано квитків: 214 на суму 214 000 ₴.
Ми автоматично повернемо покупцям 100% — 214 000 ₴. Скасувати повернення не можна.
Причина — покупці її побачать: [____]
[Ні]  [Так, скасувати подію]»

Після підтвердження подія стає 'cancelled', продаж закривається, а КОЖНЕ оплачене замовлення потрапляє в чергу повернень. Черга виконує рефанди фоново з ретраями і бекофом — саме тому, що зовнішній провайдер може відповісти 429 або 500, а 214 покупців не можна лишити наполовину поверненими.

Покупець одразу (не після виконання рефанду) бачить у квитку: «Подію скасовано. Причина: {причина}. Повертаємо 100% — 1000 ₴ на той самий спосіб оплати, зазвичай 5–10 робочих днів.» Квиток стає неактивним, QR не показується. Push і лист ідуть тим самим текстом.

Організатор бачить прогрес: «Повернення: 187 із 214 виконано, 27 в черзі». Якщо якесь повернення провалилось після всіх спроб — окремий рядок «3 повернення потребують уваги» з кнопкою «Повторити» і поясненням причини від провайдера.

ТОЙ САМИЙ механізм використовується для ручного масового повернення без скасування: «Повернути кошти всім» на події (наприклад, організатор передумав уже після продажів) — та сама черга, initiator='organizer'.

sweep і create_payout скасовану подію не чіпають (умова додана в REF-2 і тут перевіряється тестом як контроль).

## Зміни в API

`POST /api/events/:id/cancel` з тілом `{ reason: String }` → `{ orders_queued: i64, amount_total: Decimal }`. Наявний `DELETE /api/events/:id` лишається сумісним: викликає той самий код із reason=null і теж ставить черги (сьогодні він мовчки лишає гроші — це і є дефект).
`POST /api/organizer/events/:id/refund-all` з `{ reason: String }` — той самий шлях без скасування події.
`GET /api/organizer/events/:id/refunds/progress` → `{ total, done, pending, failed }`.
`POST /api/organizer/refund-jobs/:id/retry` — ручний повтор провального.
Новий воркер у `main.rs` поруч із наявними escrow_worker/email_worker: бере пачку задач `pending`, кличе `provider.refund` через seam (до підключення справжнього PSP — TestProvider), пише результат.

## Зміни в базі

Міграція `0044_refund_jobs.sql`:
CREATE TABLE refund_jobs (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  order_id UUID NOT NULL UNIQUE REFERENCES orders(id) ON DELETE CASCADE,
  amount NUMERIC(12,2) NOT NULL CHECK (amount > 0),
  status TEXT NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','processing','done','failed')),
  attempts INT NOT NULL DEFAULT 0,
  next_attempt_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  last_error TEXT,
  initiator TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX refund_jobs_due_idx ON refund_jobs (next_attempt_at) WHERE status = 'pending';
UNIQUE(order_id) — це і є захист від подвійного рефанду: повторне скасування або повторний запуск не створять другу задачу.
Плюс `events` += `cancel_reason TEXT`, `cancelled_at TIMESTAMPTZ`.

## Критерії приймання (AC)

- Скасування події з 3 оплаченими замовленнями створює рівно 3 рядки refund_jobs зі status='pending' і сумою = повній amount кожного (100%, а не за політикою).
- Подія з політикою 'none': після скасування покупці все одно отримують 100% — політика цю гілку не обмежує.
- Повторне скасування тієї самої події не створює других задач (UNIQUE(order_id)) і повертає 200 з orders_queued=0.
- Після скасування sweep не переводить жодне замовлення цієї події ні в 'clearing', ні в 'cleared'; create_payout її не бачить.
- Воркер із провайдером, що падає з 500, лишає задачу 'pending' з attempts+1 і next_attempt_at у майбутньому (бекоф), а не 'failed' з першого разу.
- Після N спроб задача стає 'failed' з last_error, потрапляє в лічильник failed і показується організатору.
- POST retry для 'failed' повертає її в 'pending' з нульовим бекофом.
- Квиток скасованої події не віддає QR і не проходить сканування (verdict 'inactive' на POST /api/events/:id/scan).
- Покупець бачить банер із причиною ОДРАЗУ після скасування, ще до того як рефанд фактично виконано — гроші йдуть довше, ніж інформація.
- refund-all без скасування події ставить ті самі задачі, але подія лишається 'published' і продаж не закривається автоматично (окреме рішення організатора).
- Кожне виконане повернення пише рядок у refund_records з initiator='cancellation'.

## Що має бути відхилено (SEC)

- Скасування чужої події → 403; жодної задачі не створено.
- Повторний запуск воркера в двох репліках не виконує один рефанд двічі: перехід pending→processing через FOR UPDATE SKIP LOCKED, і UNIQUE(order_id) як другий рубіж.
- Повторна доставка відповіді провайдера (той самий рефанд підтверджений двічі) не збільшує orders.refunded_amount двічі.
- Задача не створюється для замовлень зі status='refunded' (уже повернені) — інакше подвійний рефанд при скасуванні події, де хтось уже повернувся сам.
- retry чужої задачі (job іншої події) → 403.
- cancel_reason не рендериться як HTML у веб-клієнті й у листі (текст від організатора бачать сотні покупців).
- Скасування події з квитками у стані 'used' (людей уже пропустили) не блокується, але перевіряється явним тестом: рішення — повертати теж, і воно має бути зафіксоване, а не випадкове.
- Воркер не має шляху виплатити або списати замість повернути: тест підміняє відповідь провайдера і вимагає, щоб жоден стан замовлення не пішов у 'cleared'/'paid_out'.
