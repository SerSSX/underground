# REF-2 — Снапшот політики в замовленні + узгодження ескроу: sweep не випереджає дедлайн повернення

| Поле | Значення |
|---|---|
| **Фаза** | Фаза 2 — повернення |
| **Estimation** | M |
| **Status** | `INTAKE` |
| **Критичний шлях до першого платежу** | так |
| **Depends on** | REF-1 |

## Навіщо

Політику, ПОКАЗАНУ покупцеві, і політику, яку система ЗАСТОСУЄ, не можна читати з двох різних місць у різний час — організатор змінить дати або поля events, і покупець отримає не те, що йому обіцяли. Гірше: escrow.rs::sweep рахує дозрівання коштів ВИКЛЮЧНО від COALESCE(e.ends_at, e.starts_at), а events.rs::update_event дозволяє COALESCE-оновлення starts_at/ends_at у будь-який момент без жодної перевірки на існуючі оплачені замовлення. Тобто організатор посуває ends_at у минуле — і sweep чистить кошти до того, як покупець встиг повернути квиток. Зараз це просто невідповідність станів; після підключення справжніх грошей це вкрадений рефанд. Плюс sweep не дивиться на e.status, тож кошти СКАСОВАНОЇ події спокійно дозрівають до 'cleared' і виплачуються.

## Як це працює

У момент оплати (fulfill) замовлення «фотографує» умови: який був текст політики, до якої хвилини можна повернути, скільки відсотків повернемо, чи повертається сервісний збір, і коли розрахункова дата виплати організатору. Далі жодна зміна події на це замовлення НЕ впливає.

Покупець бачить у своєму квитку рівно ту дату, яку зафіксували при купівлі. Якщо організатор потім пересунув подію на тиждень раніше — умови повернення в уже проданому квитку не погіршуються.

Кошти дозрівають так: `held` → `clearing` після фактичного кінця події (як зараз), але `clearing` → `cleared` тепер вимагає ДОДАТКОВО, щоб дедлайн повернення вже минув. Тобто виплата ніколи не випереджає можливість повернути гроші — інакше рефанд впаде в порожній баланс.

Замовлення скасованої події зі sweep випадають узагалі: їхню долю вирішує черга рефандів (REF-8), а не годинник.

І організатору забороняється рухати ціну, валюту й дати після першого оплаченого замовлення: 409 «Подію вже купують — ціну, валюту й дати змінити не можна. Якщо подія переноситься, скасуйте її: ми повернемо покупцям 100%».

## Зміни в API

`api/src/orders.rs`:
- `checkout` рахує політику через `refunds::` і кладе її в CheckoutResp (`refund_policy_text`, `refundable_until`, `refund_amount_preview`) — це те, що покупець бачить ПЕРЕД оплатою (REF-4).
- `fulfill(conn, order_id)` (транзакційний, ідемпотентний — логіку не переписуємо, лише доповнюємо той самий UPDATE) додатково пише `refund_policy_snapshot`, `refundable_until`, `payout_due_at` у той самий рядок orders. payout_due_at = max(COALESCE(ends_at, starts_at) + clearing_days, refundable_until).

`api/src/escrow.rs::sweep` — арифметика дат лишається, додаються рівно три умови:
- обидва UPDATE: `AND e.status <> 'cancelled'`;
- clearing→cleared: `AND (o.refundable_until IS NULL OR o.refundable_until < now())`;
- сигнатура і повертані лічильники без змін.

`api/src/events.rs::update_event`: якщо існує оплачене замовлення — заборонити зміну `price`, `currency`, `starts_at`, `ends_at` (409). Ця перевірка стоїть поруч із перевіркою пом'якшення політики з REF-1.

## Зміни в базі

Міграція `0041_order_refund_snapshot.sql`:
ALTER TABLE orders
  ADD COLUMN refund_policy_snapshot JSONB,
  ADD COLUMN refundable_until TIMESTAMPTZ,
  ADD COLUMN payout_due_at TIMESTAMPTZ,
  ADD COLUMN refunded_amount NUMERIC(12,2) NOT NULL DEFAULT 0 CHECK (refunded_amount >= 0);
CREATE INDEX orders_refundable_until_idx ON orders (refundable_until) WHERE escrow_status IN ('held','clearing');

Бекфіл наявних оплачених замовлень у тій самій міграції: refund_policy_snapshot з поточних полів події, refundable_until = starts_at - refund_cutoff_hours. Без бекфілу вже продані квитки залишаться з NULL і поводитимуться як «повернення без дедлайну» — саме та щілина між міграцією і гейтом, через яку проходять реальні замовлення.

## Критерії приймання (AC)

- Після pay-test (або webhook fulfill) рядок orders має непорожній refund_policy_snapshot, refundable_until і payout_due_at.
- Змінити events.starts_at на пізніший після оплати неможливо (409), а якщо адмін змінив напряму — refundable_until уже оплаченого замовлення не змінюється.
- sweep НЕ переводить clearing→cleared, поки now() < orders.refundable_until, навіть якщо clearing_days уже минули; на наступному прогоні після дедлайну переводить.
- sweep не змінює жодного замовлення події зі status='cancelled' (ні held→clearing, ні clearing→cleared).
- payout_due_at завжди >= refundable_until для того самого замовлення (властивість перевіряється тестом на кількох комбінаціях cutoff/clearing_days).
- Для політики 'none' refundable_until = NULL, і sweep поводиться як раніше (дозріває за clearing_days).
- PATCH price на події з оплаченим замовленням → 409 з текстом «Подію вже купують…»; на події без оплачених — 200.
- Бекфіл: після міграції жодне замовлення зі status='paid' і платної події не має refundable_until IS NULL при політиці, відмінній від 'none'.
- fulfill лишається ідемпотентним: повторний виклик для того самого order_id повертає None і не перезаписує снапшот.

## Що має бути відхилено (SEC)

- Організатор пересуває ends_at у минуле, щоб достроково отримати виплату → 409 на PATCH; навіть за прямої зміни в БД sweep не очистить замовлення раніше за його власний refundable_until.
- Клієнт передає refundable_until/payout_due_at/refunded_amount у тілі checkout або pay-test → поля ігноруються, рахує сервер.
- Гонка: два паралельні fulfill того самого замовлення не створюють двох снапшотів і не подвоюють нічого (перевірка на наявному FOR UPDATE).
- sweep, запущений одночасно у двох репліках API, не переводить одне замовлення двічі й не пропускає перевірку refundable_until у жодній із них.
- Замовлення в стані 'frozen' (диспут) sweep не чіпає — наявна поведінка не має регресувати після додавання нових умов.
- refunded_amount не може стати від'ємним (CHECK), навіть якщо код спробує відняти більше, ніж повертав.
