## Навіщо

Сьогодні «рефанд» у коді — це UPDATE статусу: `admin::escrow_action("refund")` і `tickets::return_ticket` не звертаються до провайдера взагалі. `events::delete_event` виконує рівно `UPDATE events SET status='cancelled', sales_closed=true` — жодного дотику до `orders`, `tickets`, ескроу; при цьому sweep (до PAY-8) доводив ці гроші до виплати. Масового повернення немає ніде: адмінський ендпоінт працює по ОДНОМУ замовленню за HTTP-виклик, тож 200 квитків — це 200 ручних викликів без ретраїв. І є асиметрія-баг: `escrow_action` повертає використання промокоду (`used_count - 1`), а `return_ticket` — ні, тож самоповернення покупцем назавжди спалює одне використання. Вимога власника №2 («можна повернути гроші») без цієї задачі не виконується.

## Як це працює

Організатор скасовує подію однією кнопкою і бачить попередження: «Буде повернено 214 квитків на суму 53 500 ₴. Продаж закриється, повернення почнуться зараз». Підтверджує → подія в стані «скасована», продаж закритий, кожен покупець отримує повідомлення й лист «подія скасована, гроші повертаються, зазвичай 5-10 робочих днів», квитки стають «повернені». В кабінеті організатора з'являється смужка прогресу «повернено 180 з 214», а рядки, що не пройшли, показані з причиною. Якщо повернення падає (тимчасова помилка провайдера), система повторює сама з наростаючою паузою до доби; якщо падає остаточно (порожній баланс організатора), рядок висить у стані «потребує уваги» і бачать його і організатор, і адмін платформи. Часткове повернення (наприклад 50% за політикою) працює тим самим механізмом — просто сума менша, і покупець бачить у своєму квитку «повернено 125 ₴ з 250 ₴».

## Зміни в API

Новий модуль `api/src/refunds.rs`. Таблиця-черга + воркер `refunds::worker` у `main.rs` (ретраї з backoff + джитер, тільки для ідемпотентних викликів; ідемпотентний ключ `refund:{order_id}:{seq}`). `POST /api/events/:id/cancel` замінює наявний `DELETE` як шлях скасування (DELETE лишається як алиас, що всередині кличе cancel): у одній транзакції ставить `status='cancelled'`, `sales_closed=true`, ставить усі `paid` замовлення події в `escrow_status='refund_due'` і створює рядки в `refund_jobs`. `refunds::enqueue(order_id, amount_minor, reason)` — єдина точка входу для всіх джерел повернення: скасування, самоповернення покупцем, адмінський рефанд, безвихідний фулфіл (PAY-3), політика повернення (задачі REF-*). `tickets::return_ticket` і `admin::escrow_action("refund")` переводяться на `refunds::enqueue` і на симетричне повернення промокоду. `GET /api/events/:id/refund-progress` — прогрес для організатора й адміна.

## Зміни в базі

Міграція 0049: `CREATE TABLE refund_jobs (id UUID PRIMARY KEY DEFAULT gen_random_uuid(), order_id UUID NOT NULL REFERENCES orders(id), amount_minor BIGINT NOT NULL CHECK (amount_minor > 0), reason TEXT NOT NULL, seq INT NOT NULL DEFAULT 1, status TEXT NOT NULL DEFAULT 'queued', attempts INT NOT NULL DEFAULT 0, next_attempt_at TIMESTAMPTZ NOT NULL DEFAULT now(), last_error TEXT, provider_ref TEXT, created_at TIMESTAMPTZ NOT NULL DEFAULT now())`; `CREATE UNIQUE INDEX refund_jobs_order_seq_uidx ON refund_jobs (order_id, seq)`; `CREATE INDEX refund_jobs_due_idx ON refund_jobs (next_attempt_at) WHERE status = 'queued'`. `orders.refunded_amount` (з PAY-1) стає авторитетною сумою вже поверненого + `refunded_amount_minor BIGINT NOT NULL DEFAULT 0` з CHECK `refunded_amount_minor <= amount_minor`.

## Критерії приймання (AC)

- Скасування події з 200 оплаченими квитками створює рівно 200 рядків у `refund_jobs` в одній транзакції і закриває продаж; повторне скасування не створює ще 200.
- Замовлення скасованої події ніколи не переходить у `cleared`/`paid_out` (control-presence: прибрати умову `status <> 'cancelled'` зі sweep — тест червоніє).
- Тимчасова помилка провайдера (5xx на моку) призводить до повторної спроби з більшою паузою; після N спроб рядок стає `needs_attention` з причиною, а не зникає.
- Часткове повернення 50% лишає `refunded_amount_minor = amount_minor / 2` і квиток у стані, визначеному політикою (не обов'язково «повернений»).
- `tickets::return_ticket` повертає використання промокоду так само, як `admin::escrow_action` (тест порівнює `used_count` після обох шляхів — сьогодні вони розходяться).
- Сума всіх успішних повернень по замовленню ніколи не перевищує сплаченої суми — CHECK тримає, і спроба поставити зайвий job відхиляється 409.
- Повернення на подію без жодного оплаченого квитка проходить без помилок і не створює порожніх рядків.

## Що має бути відхилено (SEC)

- Повернути суму більшу за сплачену неможливо жодним шляхом — ні адмінським, ні через політику, ні через кілька паралельних jobs (перевірка під `FOR UPDATE` на замовленні + CHECK).
- Подвійне повернення того самого замовлення неможливе: унікальний `(order_id, seq)` і перевірка `refunded_amount_minor` перед відправкою провайдеру.
- Скасувати подію може лише її організатор або адмін платформи; помічник із дозволом `scan` — не може (розширює наявний `staff.rs`, права не плутаються).
- Покупець не може ініціювати повернення чужого квитка — наявна перевірка `owner_id` зберігається, control-presence тест.
- Отримувач подарованого квитка (у якого `orders.buyer_id` лишився початковим) не отримує повернення на СВОЮ картку: гроші завжди повертаються на початковий засіб оплати платника — це має бути явно написано в умовах подарунка, і тест перевіряє, що інший шлях неможливий.
- Воркер повернень не запускається у двох репліках одночасно (advisory lock), інакше два паралельні рефанди по одному замовленню.
- `last_error` від провайдера санітизується перед показом організатору — жодних ключів і сирих payload-ів.
