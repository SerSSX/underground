# PAY-5 — Онбординг організатора: під'єднаний акаунт, статус із вебхука, зняття IBAN/SWIFT з нашої бази

## Навіщо

Обрана модель — прямі платежі на акаунт організатора: мерчантом по квитку є організатор, і гроші ніколи не лежать на нашому балансі. Це вимагає, щоб у організатора був власний під'єднаний акаунт, і щоб МИ знали, чи він може приймати платежі й отримувати виплати. Сьогодні `kyc.rs` — домашній гейт із валідацією IBAN/SWIFT, тобто ми зберігаємо чужі банківські реквізити, які в новій моделі нам не потрібні й не мають зберігатись (зменшення обсягу персональних даних). ВАЖЛИВО: акаунт створюється в актуальній формі API провайдера (Accounts v2 з дашбордом типу express), а не в застарілій — застарілу комбінацію провайдер прямо не рекомендує, і будувати на ній означає переписувати через рік.

## Як це працює

Організатор створює БЕЗКОШТОВНУ подію одразу, без жодних платіжних форм — стіна з'являється лише там, де без неї не можна. Коли він уперше ставить події ціну і тисне «Опублікувати», з'являється екран «Щоб отримувати гроші, під'єднайте виплати» з однією кнопкою. Кнопка веде на хостовану форму провайдера, де організатор сам вводить свої дані й банк; ми цих даних не бачимо і не зберігаємо. Повернувшись, він бачить один із трьох станів: «перевіряється» (продаж уже дозволено, виплата — ще ні), «готово» або «потрібні документи: {перелік}». Стан оновлюється сам, коли провайдер надсилає вебхук про зміну акаунта — організатору не треба тиснути «оновити». Поки акаунт не може приймати платежі, кнопка «Опублікувати платну подію» неактивна з поясненням. Раніше введені IBAN/SWIFT зникають з профілю — замість них рядок «Виплати налаштовані у {провайдер}» і кнопка «Змінити реквізити», яка веде в хостовану панель провайдера.

## Зміни в API

Розширює `kyc.rs`, не створює новий модуль. Нові методи трейта в `provider.rs`: `create_seller_account(country, email) -> Result<String>` і `seller_onboarding_link(account_ref, refresh_url, return_url) -> Result<String>` (для Noop/Test — детерміновані заглушки). Нові ендпоінти: `POST /api/me/payouts/connect` (створює під'єднаний акаунт, якщо його ще немає, і повертає URL онбордингу), `GET /api/me/payouts/status` (повертає `charges_enabled`, `payouts_enabled`, `requirements_due`, `country`). `webhooks.rs` обробляє `WebhookEvent::AccountUpdated{..}` → оновлює прапорці в `users`. `events::publish`/`create_event` для `cost_type='paid'` перевіряють `users.psp_charges_enabled = true` і повертають 409 інакше. Видаляються: `valid_iban`, `valid_swift` і ендпоінти подання/перевірки банківських реквізитів; `kyc_status` лишається як домашня агрегація прапорців провайдера.

## Зміни в базі

Міграція 0044: `ALTER TABLE users ADD COLUMN psp_account_id TEXT UNIQUE, ADD COLUMN psp_charges_enabled BOOLEAN NOT NULL DEFAULT false, ADD COLUMN psp_payouts_enabled BOOLEAN NOT NULL DEFAULT false, ADD COLUMN psp_requirements_due JSONB, ADD COLUMN psp_country TEXT`. `ALTER TABLE users DROP COLUMN payout_iban, DROP COLUMN payout_swift, DROP COLUMN payout_name` — окремою міграцією 0045 ПІСЛЯ того, як адмінська сторінка перестане їх читати (експанд-контракт: 0044 додає, код переїжджає, 0045 прибирає).

## Поверхні

**Веб.** Кабінет організатора: блок «Виплати» з трьома станами і кнопкою під'єднання; блокування публікації платної події з поясненням. Адмінка: KYC-сторінка перестає показувати IBAN/SWIFT і показує стан під'єднаного акаунта (тільки читання) + кнопку «оновити зі сторони провайдера».

**Android.** Той самий блок «Виплати» в кабінеті організатора; кнопка відкриває хостовану форму в Custom Tab і повертає в апку по `return_url` (deep link).

**Telegram Mini App.** Немає (у Фазі 5 TMA відкриває той самий URL через `openLink`, бо хостовану форму провайдера не можна вбудовувати в WebView).

## Критерії приймання (AC)

- Організатор без під'єднаного акаунта створює і публікує БЕЗКОШТОВНУ подію — 201, жодного платіжного екрану.
- Публікація ПЛАТНОЇ події без `psp_charges_enabled` — 409 з текстом про під'єднання виплат; з прапорцем — 201.
- `POST /api/me/payouts/connect` двічі поспіль не створює двох акаунтів: другий виклик повертає посилання для того самого `psp_account_id`.
- Вебхук `AccountUpdated` з `payouts_enabled=true` перемикає прапорець у БД без жодної дії організатора; `GET /api/me/payouts/status` одразу показує новий стан.
- Після міграції 0045 грепом по `api/src` немає жодної згадки `payout_iban`/`payout_swift`, а `valid_iban`/`valid_swift` видалені разом із тестами.
- `GET /api/me/payouts/status` чужого організатора недоступний — ендпоінт віддає лише власний стан.

## Що має бути відхилено (SEC)

- Організатор не може під'єднати чужий акаунт: `psp_account_id` приймається ВИКЛЮЧНО з відповіді провайдера, ніколи з тіла запиту клієнта.
- Вебхук `AccountUpdated` не дає підняти прапорці чужому користувачеві: збіг шукається за `users.psp_account_id`, невідомий акаунт — 200 без дії.
- Прапорці `psp_charges_enabled`/`psp_payouts_enabled` не редагуються жодним адмінським ендпоінтом на запис — вони є дзеркалом провайдера; адмін може лише заблокувати організатора окремим прапорцем `blocked`.
- Заблокований (`blocked`) або видалений за GDPR організатор не може публікувати платну подію навіть із увімкненими прапорцями провайдера.
- URL онбордингу одноразовий і короткоживучий: повторний GET того самого посилання після використання не дає доступу до чужої форми (перевіряється тим, що ми ніколи не зберігаємо URL у БД і не віддаємо його іншому користувачеві).
- Видалення IBAN/SWIFT робиться після переїзду коду, а не одночасно — тест на міграції 0044 перевіряє, що стара колонка ще читається, тест на 0045 — що код її вже не читає.
