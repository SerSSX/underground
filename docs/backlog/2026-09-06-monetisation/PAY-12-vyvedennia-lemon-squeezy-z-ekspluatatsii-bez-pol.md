# PAY-12 — Виведення Lemon Squeezy з експлуатації без поломки наявних замовлень

| Поле | Значення |
|---|---|
| **Фаза** | Фаза 1 — гроші |
| **Estimation** | M |
| **Status** | `INTAKE` |
| **Критичний шлях до першого платежу** | ні |
| **Depends on** | PAY-1, PAY-4, PAY-7 |

## Навіщо

Наявна LS-інтеграція нежива за ПОЛІТИКОЮ, а не за конфігурацією: цей клас провайдерів (merchant of record) забороняє і маркетплейс, і виконання поза власним сайтом, тобто квиткову платформу він не обслуговуватиме ніколи. `webhooks.rs::lemonsqueezy`, чотири поля `ls_*` у `payment_settings`, гілка `ready_for_live` у `payments.rs` і склеювання URL у `orders::checkout` — це код під провайдера, якого не буде. Його треба видалити, а не добудовувати. Але видаляти можна лише після переїзду: на дев-стенді вже є замовлення з `provider = 'lemonsqueezy'` і з ним же в сіді, тож наївний DROP колонок або зміна значень `provider` зламає наявні рядки й адмінські екрани. Це задача про безпечний порядок, а не про видалення.

## Як це працює

Для будь-якого користувача — нічого не змінюється. Адмін на сторінці платіжок більше не бачить полів Lemon Squeezy: замість чотирьох порожніх рядків там ключі нового провайдера. Наявні старі замовлення в адмінці й далі відкриваються, показують свій провайдер як «lemonsqueezy (архів)» і не пропонують по них жодної дії, яка потребує провайдера (рефанд через провайдера по них неможливий — вони позначені як історичні). Спроба поставити `provider = 'lemonsqueezy'` в налаштуваннях відхиляється: цей провайдер більше не підтримується.

## Зміни в API

Видаляються: маршрут `POST /api/webhooks/lemonsqueezy`, функції `webhooks::sign`/`verify_signature` (їх заміщає `psp::verify_webhook` з PAY-7), поля `ls_*` у `PaymentSettings`/`SettingsView`/`ReadinessView`/`UpdateSettingsReq`, гілка `ready_for_live` під lemonsqueezy, склеювання LS-URL у `orders::checkout` (уже прибране в PAY-1 — тут прибирається залишок конфігурації). `payments::update_settings` відхиляє `provider = "lemonsqueezy"` з 400 і переліком дозволених імен. `admin::orders` позначає історичні замовлення прапорцем `legacy_provider: true`.

## Зміни в базі

Порядок експанд-контракт, три кроки в двох міграціях. 0050: `UPDATE orders SET provider = 'lemonsqueezy_archived' WHERE provider = 'lemonsqueezy'` (значення лишається читабельним, але жоден код більше не намагається його резолвити); `ALTER TABLE payment_settings ALTER COLUMN provider SET DEFAULT 'test'` і `UPDATE payment_settings SET provider = 'test' WHERE provider = 'lemonsqueezy'`. 0051 (після деплою коду, що більше не читає ці поля): `ALTER TABLE payment_settings DROP COLUMN ls_api_key, DROP COLUMN ls_store_id, DROP COLUMN ls_variant_id, DROP COLUMN ls_webhook_secret`. Колонки `orders.provider` НЕ чіпаємо — історія має лишитись читабельною.

## Поверхні

**Веб.** Адмінка → Платіжки: блок Lemon Squeezy зникає. Адмінка → Замовлення: у старих рядках провайдер підписаний «архів», дії по провайдеру приховані.

**Android.** Немає.

**Telegram Mini App.** Немає.

## Критерії приймання (AC)

- Грепом по `api/`, `web/` і `admin/` слово `lemonsqueezy` зустрічається лише в міграціях і в одному місці — мапінгу підпису «архів» в адмінці.
- Наявні замовлення з дев-стенда після міграції відкриваються в адмінці й показують суму, статус і подію; жоден екран не падає.
- `PATCH /api/admin/payment-settings` з `provider = "lemonsqueezy"` — 400 з переліком дозволених значень.
- Старий маршрут `POST /api/webhooks/lemonsqueezy` повертає 404 після видалення (а не 500).
- Міграція 0051 застосовується на копії дев-бази без помилок, і `scripts/ci.sh` лишається зеленим (покриття 100%).
- Жоден тест не був послаблений або видалений заради цієї зачистки: видалені тільки ті тести, що перевіряли видалений код, і це перелічено в описі коміту (§5 — тести це храповик).

## Що має бути відхилено (SEC)

- Видалення полів `ls_*` не лишає секрет у бекапі логів чи в `admin_actions` — перевіряється пошуком по значеннях у журналі дій.
- Старий вебхук-маршрут не лишається живим і не приймає підпис під старим секретом (інакше це відкритий шлях мінтити квитки).
- Історичні замовлення з архівним провайдером не можна провести через `refunds::enqueue` — 409 з поясненням, замість спроби викликати неіснуючий адаптер.
- Міграція, що переписує `orders.provider`, не чіпає жодного іншого поля — перевіряється порівнянням хешу решти колонок до і після на копії дев-бази.
- Порядок міграцій дотримано: 0051 не застосовується разом із деплоєм коду, що ще читає `ls_*` — інакше вікно, у якому API падає на кожному `load_settings`.
