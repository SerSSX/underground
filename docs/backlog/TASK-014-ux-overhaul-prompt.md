### Контекст і проблема

Апка будувалась швидкими ітераціями «фіча за фічею» як спроба реалізувати наявний дизайн
із Figma (файл "underground", id `hZvaYaoCKfr1XyqqkdAHJ4`, 44 фрейми — node-ids у пам'яті проєкту).
Функціональний кістяк хороший і покритий тестами (107 бекенд-тестів, lines 100%), але **UI/UX вийшов
сирий**: екрани збирались без системи, місцями не відповідають дизайну, виглядають неохайно.
Завдання цієї сесії — **систематично довести продукт до стану «вилизано до блиску»**: логічно,
зручно, красиво, повноцінний сервіс на трьох поверхнях (мобайл + веб-кабінет організатора + адмінка платформи).

Що вже працює (бекенд + Android): email/пароль auth, онбординг з інтересами, афіша з фільтрами API,
деталі події з медіа (постер-аплоад, галерея, відео, соцлінки), безкоштовні квитки + платні (test-режим,
ескроу held), e-квиток QR + скан на вході, повернення/передача квитка, створення/редагування/приховування/
скасування події, стоп-продажів, профілі зі стіною (автопости анонсів та відгуків, лайки, коменти),
підписки на будь-кого, стрічка (підписки ∪ інтереси), відгуки з рейтингом організатора, сповіщення
за prefs, чат юзер↔організатор, веб-адмінка платежів (Next.js, лише сторінка payment-settings).

### Ключове продуктове рішення (зафіксоване)

**Кожен юзер може бути і відвідувачем, і мейкером.** Ніякої окремої реєстрації організатора.
Продумай, як це виразити в UX: перемикач/режим у налаштуваннях профілю («Режим організатора»),
прогресивне розкриття (функції мейкера з'являються після першої створеної події), або таб «Мої»
що адаптується. Обери і обґрунтуй.

### Фаза 0 — Підготовка (інфра)

1. `docker compose up -d` (Postgres на :5544, API на :8080). Акаунти (пароль `underground`):
   `user@underground.dev`, `maker@underground.dev`, `admin@underground.dev`.
2. Телефон moto g05 по USB: `scripts/device-run.sh` (adb reverse + install). Скріни:

3. Перевір, що Figma MCP працює: інструменти `mcp__figma*` (get_image / get_code за node-id).

4. УВАГА: диск майже повний; перед великими білдами перевір `df -h /` (рецепт чистки в пам'яті проєкту).

### Фаза 1 — Аудит (нічого не переробляй, тільки фіксуй)

**1а. Дизайн-аудит (Figma ↔ реалізація).** Пройди всі 44 фрейми (node-ids в пам'яті проєкту,
URL-форма `A-B` → API-форма `A:B`). Для кожного: get_image → знайди відповідний екран в апці →
скрін з телефона → зафіксуй у таблиці: `фрейм | екран | статус (відповідає/частково/відсутній) |
розбіжності`. Окремо винеси **дизайн-токени** з Figma: палітра, типографіка (шрифти/розміри/ваги),
радіуси, спейсинги, іконографія, стилі карток/кнопок/чипів — порівняй з `ui/theme/` і компонентами.

**1б. UX-аудит (usability walkthrough).** Пройди на телефоні ключові journeys, на кожному кроці
фіксуй фрикції (зайві тапи, незрозумілі лейбли, відсутні loading/empty/error стани, мертві кінці,
відсутній зворотний зв'язок, недосяжні дії):
- Новачок: реєстрація → онбординг → знайти подію (пошук/фільтри — UI фільтрів ще НЕМає, API є!) →
  деталі → купити квиток → e-квиток → відгук після події.
- Мейкер: створити подію з медіа → побачити її в афіші → керувати (редагувати/стоп-продажі) →
  сканувати QR на вході → відповісти покупцю в чаті → подивитись «фінанси» (зараз НЕМає екрана).
- Соціальний: стрічка → відкрити автора → підписатись → стіна → лайк/комент → повідомлення.
Оціни кожен екран за евристиками Нільсена + Material 3 чеклістом (стани, доступність, типографіка).

**1в. Технічний аудит UI-шару:** консистентність компонентів (картки/кнопки/відступи різнобій?),
локалізація (укр всюди? хардкод?), оброблення помилок мережі, оффлайн-поведінка, продуктивність
списків. Бекенд: чого бракує для повного UX (наприклад: пошук UI потребує date_from/price_max в API,
лічильник непрочитаних для бейджів на табах, аватар-аплоад).

**Делівербл:** `docs/audit/2026-06-XX-ux-audit.md` — таблиця фрейм↔екран, список проблем із
severity (P0 блокер UX / P1 серйозно / P2 полірування), знахідки по токенах.

### Фаза 2 — Концепція (перед кодом, на рев'ю користувачу)

1. **Інформаційна архітектура:** фінальна структура табів і навігації; як живе дуальність
   юзер/мейкер; де живуть повідомлення/сповіщення (бейджі непрочитаного на табах).
2. **Дизайн-система:** `ui/theme` переписати під токени з Figma; єдині компоненти
   (UButton, UCard, UChip, UTextField, EmptyState, ErrorState, Avatar, RatingStars...).
3. **Спека кожного екрана** (стан-машина loading/empty/error/content + дії) — коротко, у
   `docs/specks/SDD-014-*.md` за доктриною.
4. Узгодь з користувачем ДО реалізації (делівері частинами з паузами на рев'ю — доктрина).

### Фаза 3 — Веб-кабінет організатора (продумати + спланувати, потім будувати)

Розширити `admin/` (Next.js 15) або окремий розділ `/organizer` (логін той самий, JWT):
повноцінне робоче місце мейкера, дублює і розширює мобільний функціонал:
- **Дашборд:** продажі по подіях, виручка, стани ескроу (held/cleared/paid_out), к-сть проданих/валідованих квитків.
- **Події:** таблиця + CRUD з усіма медіа (постер/галерея/відео/лінки), статуси, стоп-продажі, дублювання події.
- **Квитки/відвідувачі:** список покупців по події, статуси квитків, ручна валідація, експорт CSV.
- **Чати:** діалоги з покупцями (той самий messages API).
- **Фінанси:** баланс по станах ескроу, історія транзакцій, запит на виплату (payout request → черга в адмінці).
- **Профіль організатора:** аватар/біо/соцлінки (це публічний профіль в апці).
Бекенд-добавки, які знадобляться: ендпоінти агрегатів продажів по організатору, список квитків
події (organizer-only), payout requests. Все за доктриною: беклог → спека → тести (тримати lines 100%).

### Фаза 4 — Адмін-панель платформи (для власника)

Розширити `admin/` до повноцінної панелі керування:
- **Dashboard:** GMV, комісія платформи, к-сть юзерів/подій/квитків, графіки по днях.
- **Users:** пошук/список, блокування/розблокування, зміна ролі, перегляд активності.
- **Events:** модерація (published/hidden/blocked), черга скарг (complaints — треба буде модель).
- **Payments:** УСІ замовлення і транзакції з фільтрами; стани ескроу з ручними діями
  (refund / freeze / release / payout); налаштування провайдерів (Lemon Squeezy ключі, test/live mode —
  вже є) + **комісія платформи**: глобальна (bps, вже є поле) і продумати per-organizer override.
- **Payouts:** черга запитів на виплату від організаторів: approve/reject, позначка виплачено.
- Технічно: захист CurrentAdmin вже є; нові admin-ендпоінти з тестами; UI — таблиці з пагінацією,
  пошуком; той самий темний стиль.
